#### Implementation Details

Update `packages/dotnet/README.md` with a section immediately after the exact
window-comparison introduction and before assessment/artifact workflow. It must
include this final-shaped journey, adjusted only for names that actually land:

```csharp
using Spanfold.Episodes;

var result = pipeline.History
    .CompareEpisodes("Provider QA")
    .Target("reference", selector => selector.Source("provider-a"))
    .Against("detector", selector => selector.Source("provider-b"))
    .Within(scope => scope.Window("DeviceOffline", TemporalAxis.Timestamp))
    .Normalize(normalization => normalization.OnEventTime())
    .StitchGapsUpTo(TimeSpan.FromMinutes(2))
    .RelateWithin(TimeSpan.FromSeconds(30))
    .Run();

Console.WriteLine(result.Summary.TargetMatchRate);
Console.WriteLine(result.AgainstEpisodes.Summary.MultiFragmentEpisodeRate);
Console.WriteLine(result.Summary.SplitTargetRate);

var scorecard = result.AsReference();
Console.WriteLine(scorecard.Recall);
Console.WriteLine(scorecard.Precision);
```

The section must explain the analytical distinction with one concrete example:
a reference outage `[10:00, 10:30)` and two detector fragments
`[10:02, 10:10)` / `[10:12, 10:28)`. With the documented two-minute stitch
tolerance, the detector produces one internally multi-fragment episode, not a
`Split` relation. Show that exact comparison answers where coverage differs,
while episode analysis answers that the same occurrence was observed late,
recovered early, and retained two fragments. Then explain that lowering the
stitch tolerance below the two-minute gap would form two detector episodes and
classify the cross-side component as `Split`. Do not call the gap active or
describe the two fragments as a continuous window.

Document the two tolerances separately:

- stitch tolerance relates fragments within one side and changes episode
  formation/count;
- relation tolerance associates already-formed episodes across sides and does
  not change active coverage.

Document the relation-kind table exactly:

| Kind | Meaning |
|---|---|
| One-to-one | One target occurrence relates to one against occurrence. |
| Split | One target occurrence relates to multiple against occurrences. |
| Merge | Multiple target occurrences relate to one against occurrence. |
| Complex | Multiple occurrences exist on both sides of one component. |
| Unmatched target | A target occurrence has no related against occurrence. |
| Unmatched against | An against occurrence has no related target occurrence. |

Explain that the graph is intentionally not reduced to nearest pairs. Explain
that fragments remain authoritative, the envelope measures elapsed extent, and
active magnitude is the fragment union.

Document live behavior without overclaiming: episode/relation finality includes
tolerance settling at an explicit horizon, but Spanfold does not own event-time
watermarks and cannot promise that no late record will arrive later.

Document neutral and reference modes:

- `result.AgainstEpisodes.Summary.MultiFragmentEpisodeRate` measures retained
  internal source fragmentation;
- `result.Summary` uses target/against match, coverage, count-bias,
  split-target, merge-against, and one-to-one latency terms;
- `result.AsReference()` is the explicit opt-in that interprets target as the
  reference and returns recall/precision/F1 plus missed/unexpected counts;
- do not use false-positive/false-negative language on the neutral result.

No package version or release tag changes in this task.

#### Misinterpretations To Prevent

- Wrong interpretation: “Episodes supersede exact comparison.”
  Correct rule: document them as complementary answers over the same evidence.
- Wrong interpretation: “A stitched envelope is continuous active time.”
  Correct rule: fragments are active evidence; the envelope includes internal
  inactive gaps.
- Wrong interpretation: “Precision and recall always apply because the API has
  target and against sides.”
  Correct rule: those terms appear only after explicit reference projection.
- Wrong interpretation: “Add a polished sample app to make the feature real.”
  Correct rule: use the tested library journey in documentation; no new app.
- Wrong interpretation: “Update Rust’s parity table optimistically.”
  Correct rule: state .NET-only availability and defer Rust parity.
- Wrong interpretation: “Live final means no future late event can revise the
  analysis.”
  Correct rule: document horizon-relative settling and the absence of a
  watermark contract.
