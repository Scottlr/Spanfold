### T003 — Relate episode sets as a component graph

#### Objective

Add a staged `CompareEpisodes(...)` workflow that forms target and against
episodes from one `WindowHistory`, relates their actual fragments by overlap or
proximity, and returns deterministic connected components without forcing a
false one-to-one assignment.

#### Scope

- Add the episode-comparison plan, builder, relation policy, relation kind,
  component metrics, immutable result, and `CompareEpisodes(...)` extension.
- Reuse T002 formation for both sides with one shared scope, normalization, and
  stitch policy.
- Implement a deterministic bipartite graph over compatible target/against
  episodes and classify every connected component.
- Calculate component-level active overlap, coverage, IoU, proximity, onset,
  recovery, and duration deltas from real fragments.
- Carry historical/live finality into components and apply relation-settling
  semantics at an explicit horizon.
- Add focused graph and consumer-journey tests under the Episodes test folder.

#### Out of Scope

- No greedy, nearest-only, Hungarian, or configurable assignment algorithm.
- No comparison of independently produced/persisted `EpisodeSet` objects and no
  cross-history key-comparer negotiation.
- No multiple `Against(...)` sides, cohort source, source matrix, or pairwise
  matrix in v1.
- No cross-window sequence/journey/causal API. Both sides use the one window
  family selected by `Within(...)`.
- No aggregate summary distributions or reference precision/recall; T004 owns
  those projections.
- No assessment rules, artifacts, CLI commands, persistence, dashboards, or
  Rust changes.

#### Blocked By

T002.

#### Why It Is Blocked

The graph must consume immutable, correctly grouped `Episode` values and their
configured key comparers, fragment ranges, metrics, IDs, and live finality from
T002. Reimplementing formation inside comparison is forbidden.

Exactly one target and one against selector are required. A second
`Against(...)` call must throw `InvalidOperationException` rather than silently
combine sources into a graph with ambiguous source meaning. The scope must name
one window family. The same axis-resolution, tolerance-overload, known-at, and
live-horizon rules from T002 apply to both stitch and relation tolerances. A
configured `OpenWindowHorizon` is honored by `Run()`; `RunLive(horizon)` creates
the effective plan only when neither known-at nor an open-window horizon was
already configured.

Use a closed relation kind:

```csharp
public enum EpisodeRelationKind
{
    OneToOne = 0,
    Split = 1,
    Merge = 2,
    Complex = 3,
    UnmatchedTarget = 4,
    UnmatchedAgainst = 5
}
```

The direction is part of the public contract:

- `Split`: one target episode and two or more against episodes;
- `Merge`: two or more target episodes and one against episode;
- `Complex`: two or more episodes on both sides;
- unmatched kinds contain exactly one episode on their named side and none on
  the other.

Use these component contracts:

```csharp

    public EpisodeRelationKind Kind { get; }

public sealed record EpisodeComparisonResult
{
    internal EpisodeComparisonResult(
        EpisodeComparisonPlan plan,
        EpisodeSet targetEpisodes,
        EpisodeSet againstEpisodes,
        IReadOnlyList<EpisodeRelation> relations,
        TemporalPoint? evaluationHorizon);

    public string Name => Plan.Name;
    public EpisodeComparisonPlan Plan { get; }
    public EpisodeSet TargetEpisodes { get; }
    public EpisodeSet AgainstEpisodes { get; }
    public IReadOnlyList<EpisodeRelation> Relations { get; }
    public TemporalPoint? EvaluationHorizon { get; }
}
```

`EpisodeRelationMetrics` semantics are exact:

- magnitude units are positions or timestamp ticks according to `TimeAxis`;
- target/against active magnitude is the union of every fragment on that side
  of the component;
- overlap is the intersection magnitude of the two side unions;
- coverage ratios divide overlap by the corresponding side magnitude and are
  null for a zero denominator;
- IoU is `overlap / (target + against - overlap)` and is null for an empty
  union;
- minimum gap is zero when active fragments overlap or touch, the smallest
  positive fragment-to-fragment distance when both sides exist, and null for an
  unmatched component;
- onset delta is earliest against start minus earliest target start;
- recovery delta is latest against end minus latest target end;
- active-magnitude delta is against union magnitude minus target union
  magnitude;
- elapsed-magnitude delta is against component envelope magnitude minus target
  component envelope magnitude;
- all signed deltas are null when either side is absent. Positive onset/recovery
  values mean the against side is later.

Create the runtime entry point:

```csharp
internal static class EpisodeRelationRuntime
{
    internal static EpisodeComparisonResult Run(
        WindowHistory history,
        EpisodeComparisonPlan plan);
}
```

The runtime must derive two internal `EpisodeFormationPlan` values from the one
comparison plan and invoke `EpisodeFormationRuntime.Run(...)` once per side. It
must not form episodes by reading `ComparisonResult` rows. The target set plan
uses `TargetName` and `Target.WithName(TargetName)`; the against set plan uses
`AgainstName` and `Against.WithName(AgainstName)`. Both derived plans carry the
same effective scope, normalization, formation policy, and horizon as the
comparison result.

After formation and before graph construction, compare the two sets' fragment
`WindowRecordId` values. If any normalized source record appears on both sides,
throw `InvalidOperationException` naming the record ID and both selector names.
Do not silently drop the duplicate or permit a source record to match itself.

Build the relationship graph as follows:

1. index episodes by window name, configured key equality, partition, temporal
   axis, and timestamp clock; source is intentionally not a relation boundary;
2. add a target↔against edge only when at least one pair of actual fragments
   overlaps/touches or has a gap less than or equal to relation tolerance;
3. never use envelope overlap to add an edge;
4. include isolated target and against nodes;
5. traverse the bipartite graph into connected components;
6. classify by target/against cardinality using the enum above;
7. calculate metrics from unioned fragment ranges;
8. deterministically sort episodes inside components and components inside the
   final result, independent of dictionary or traversal insertion order.

Every episode must occur in exactly one component. A chain of edges remains one
component even when its endpoints are not directly related; do not break it
into locally convenient pairs.

For live execution, a relation is `Provisional` when any member episode is
provisional or when `evaluationHorizon <= latestComponentFragmentEnd +
relationTolerance`. It becomes final only after both conditions clear. Use
overflow-safe temporal arithmetic. Historical execution over final episodes
produces final relations. `EpisodeComparisonResult.Plan`,
`TargetEpisodes.Plan`, and `AgainstEpisodes.Plan` must all describe the same
effective live horizon used for execution.

All signed deltas use `TemporalMagnitudeMath.SaturatingSubtract(...)`, and
tolerance-boundary additions use `TemporalMagnitudeMath.SaturatingAdd(...)`.
Wraparound is never an allowed result.

#### Migration Notes

The feature is additive and does not change raw comparison behavior. Target and
against terminology matches the existing staged comparison API, but episode
relation IDs and schemas are not added to existing artifacts. The v1 plan
allows one against side only; consumers needing several providers run explicit
pairwise episode comparisons.

#### Misinterpretations To Prevent

- Wrong interpretation: “Choose the nearest against episode for each target.”
  Correct rule: build the full bipartite graph and classify connected
  components; nearest assignment hides split/merge evidence.
- Wrong interpretation: “Envelope overlap proves two episodes are related.”
  Correct rule: an edge requires fragment overlap/touch/proximity; internal
  inactive gaps are not evidence.
- Wrong interpretation: “Count each graph edge as a match.”
  Correct rule: relationships are components, and each episode occurs once.
- Wrong interpretation: “If target and against selectors select the same
  window, let it match itself.”
  Correct rule: reject overlapping `WindowRecordId` membership before graph
  creation; self-matches are analytically meaningless.
- Wrong interpretation: “Relation tolerance can merge fragments into an
  episode.”
  Correct rule: stitch tolerance owns formation; relation tolerance only owns
  cross-side edges and live relation settling.
- Wrong interpretation: “A matched relation is final as soon as both current
  episodes close.”
  Correct rule: the relation remains provisional until the horizon passes the
  relation settling boundary.
- Wrong interpretation: “Complex components should be automatically reduced to
  pairs for nicer latency metrics.”
  Correct rule: preserve their multiplicity; T004 excludes ambiguous components
  from one-to-one distributions.

#### Invariants

- Formation runs exactly once per side through T002's runtime.
- Target and against use the same history, scope, normalization, and stitch
  policy.
- Edge eligibility uses actual fragments.
- Graph components are exhaustive, mutually exclusive, and deterministic.
- Target and against fragment lineage is disjoint.
- Split/merge naming is directional and stable.
- Relation metrics never inflate active coverage with tolerance or envelopes.
- Ratios are null for empty denominators.
- Positive onset/recovery deltas mean against is later.
- Live finality honors both episode and relation settling.
- No raw comparison rows or persisted artifacts are mutated.
